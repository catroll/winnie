# Voice wake and voice turns

The phone listens for one word — "winnie" — and opens a hands-free turn. The
wake itself costs nothing: it runs on the phone, offline, from an Apache-2.0
model. The utterance that follows the wake is uploaded and transcribed by the
server, so that part is billed like any other ASR call.

This document records why the detector is built this way, what Android does and
does not allow, and what still has to be measured on a real phone.

## Why on-device keyword spotting

A cloud "always listening" design cannot be zero-cost: the audio would stream
continuously, and the bill would grow with every hour the phone is on. A
recognizer that runs only after a press is not hands-free. The only design that
satisfies "say the word, pay nothing" is a small model on the phone that listens
for exactly one phrase and ignores everything else.

| Option | License | "winnie" without training | On-device size | Fit |
|---|---|---|---|---|
| **sherpa-onnx KWS** (chosen) | Apache-2.0 | yes, open vocabulary | ~5.3 MB int8 | good |
| openWakeWord | Apache-2.0 | no, one trained model per phrase | a few MB per model | training pipeline needed |
| Picovoice Porcupine | proprietary | yes, trained in its console | tiny | free only for personal non-commercial use |
| Vosk, grammar-constrained | Apache-2.0 | approximated by a word grammar | 40 MB+ | decodes continuously, heavier battery |
| Android `SpeechRecognizer` | system | not a keyword detector | 0 | requires the app in front, cannot run always-on |

sherpa-onnx wins on the property that matters here: **the keyword is data, not a
model**. It is a tiny streaming transducer trained as an open-vocabulary
keyword spotter, so a new phrase is a line in a text file — no training data, no
account, no per-keyword licence.

The model is `sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20` from the official
KWS release. It is bilingual, which matters for a Chinese owner who says an
English name: the same model can hold a Chinese keyword later without a second
detector. Only the int8 encoder, the fp32 decoder, the int8 joiner and
`tokens.txt` ship in the APK (~5.3 MB); the fp32 encoder and the test wavs in
the release tarball are not committed.

## The keyword file

`apps/android/app/src/main/assets/kws/keywords.txt`:

```
W IH1 N IY0 @winnie
W EH1 N IY0 @winnie
W IY1 N IY0 @winnie
W IH1 N IY1 @winnie
HH EY1 W IH1 N IY0 @hey_winnie
HH EY1 W EH1 N IY0 @hey_winnie
```

Four pronunciations of one word, not four keywords: the spotter matches the
exact phoneme sequence the model decodes, and different voices produce
different vowels. The measured example is below — a real speaker's "Winnie"
decodes as `W EH1 N IY0`, so a file holding only `W IH1 N IY0` never fires for
that voice. The variants are the cheap way to cover accents without a training
pipeline; each line is one more hypothesis and one more chance of a false
accept, which is why the set stays at four and not twenty.

Each line is the token sequence, then an optional boosting score (`:`) and
trigger threshold (`#`), then the text reported on a detection (`@`). The tokens
are CMU phonemes looked up in the model's `en.phone`, generated by

```
sherpa-onnx-cli text2token --tokens tokens.txt \
  --tokens-type phone+ppinyin --lexicon en.phone keywords_raw.txt keywords.txt
```

The two knobs are the whole false-accept tuning surface: a higher boosting score
and a lower threshold make a wake easier (more false accepts), the reverse makes
it harder (more misses). `1.5` / `0.25` are the library defaults; the numbers
move only after a measurement on a real phone (see "What is not verified").

`numTrailingBlanks = 0` is set in `WakeWordDetector`. The default of two blank
frames means "fire only after a short pause", which is right for a dictation
trigger and wrong here: a person saying "winnie, what is the weather" often runs
the words together, and the measured real recording only fired at zero. The cost
is that a partial match can trigger sooner, which is what the phone measurement
has to quantify.

Two phrases rather than one is deliberate. "Winnie" alone is a short, common
word; "hey winnie" is the phrase to prefer in a room with a television. Both are
in the file so the tunable is a data change, not a rebuild.

## The flow

```
WakeWordService (foreground, microphone)
  └─ SherpaWakeWordDetector: AudioRecord 16 kHz mono, 100 ms blocks
       ├─ PcmRingBuffer: last 2 s, so the turn does not lose its first words
       └─ KeywordSpotter: detection → stop the detector, release the microphone
            ├─ notification with a PendingIntent into the chat
            └─ startActivity with the pre-roll in the intent extras
                 └─ MainActivity → AppContainer.requestVoiceTurn(preRoll)
                      └─ ChatViewModel.startVoiceTurn: record until silence
                           └─ POST /api/v1/assistant/transcribe (WAV)
                                └─ sendText(transcript) — the normal chat turn
```

The pre-roll is two seconds of 16 kHz mono (64 KB), small enough to travel in an
intent extra. Without it every utterance would start after the words that
followed the wake word, because the model needs ~320 ms of context and the
activity takes a moment to open.

The end of the spoken turn is decided on the phone by `EndpointDetector`: after
speech has been seen, 1.2 s of silence ends the turn; a turn with no speech ends
after 6 s; a turn that never stops ends at 20 s. The rules are pure Kotlin and
unit tested, because they decide the shape of every voice interaction and a
device is not needed to prove them.

## The console's voice conversation

The admin console's chat page has the same capability without the wake word: the
microphone button in the composer starts a voice conversation, and the composer
is replaced by a status bar until it ends. There is no always-on listening in a
browser tab, and none is wanted.

```
composer microphone button → useVoiceConversation
  └─ recorder.ts: getUserMedia → AudioWorklet → VoiceEndpointer
       └─ 16 kHz mono WAV (OfflineAudioContext resample, hand-written header)
            └─ POST /api/v1/assistant/transcribe
                 └─ submit() — the normal chat turn, shown as a user message
                      └─ reply → speech.ts: speakableText → SpeechSynthesis
                           └─ listen again, until Cancel
```

The numbers are the phone's, not a second tuning: `VoiceEndpointer` keeps
`EndpointDetector`'s 20 ms frames, -38 dBFS speech floor, three frames to accept
speech, 1.2 s of trailing silence, and the 6 s / 20 s limits. A voice turn must
feel the same whichever client the owner is holding, and the phone's values were
chosen for a microphone at arm's length, which is how a desk console is used.
The port is pure TypeScript with the same rule structure; the browser tests
drive it through the UI.

One rule is the console's own. Opening a suspended capture device is not silent:
the analog stage settles with a thump (measured -11 dBFS on the rear microphone
here) that clears the -38 dBFS floor, so the first three frames used to count as
speech and the trailing-silence rule then ended the turn ~1.3 s after the
microphone opened — before the owner had said a word. `recorder.ts` therefore
feeds the endpointer nothing for the first 400 ms of audio; the samples are still
recorded and uploaded, so an owner who starts talking immediately loses nothing
but the decision. The phone has no such grace because its first audio is the
wake word's pre-roll.

One guard is new here. The rules count audio, so a microphone that stops
delivering blocks — unplugged, suspended by the OS, a stalled audio graph —
would leave the bar in "Listening…" for ever. `recorder.ts` ends the turn after
3 s without a block, and at 25 s wall-clock regardless. The phone has the same
guard for the same reason ("a microphone that returns silence forever must not
pin the sheet").

**Capture is PCM, not MediaRecorder.** `MediaRecorder` produces WebM/Opus, and a
recording-file ASR API is not reliably an Opus decoder; the phone already sends
16 kHz mono WAV, so the console encodes the same container itself. A worklet
hands 128-frame blocks to the page, an `OfflineAudioContext` resamples the
device rate (48 kHz here) to 16 kHz, and the WAV header is written by hand. The
processor lives in `apps/admin/public/` because `audioWorklet.addModule` needs a
real URL: Vite inlines a small `?url` import as a `data:` URL, which is not a
reliable place to load a worklet module.

**Spoken replies use the browser, not a vendor.** The reply is reduced to
sentences (code blocks dropped, links and emphasis stripped, tables flattened),
the language is chosen from the reply's script, and the platform's voices speak
it. There is no TTS binding and no per-character bill: an ASR call per turn is
the cost, and voice *output* does not need to leave the machine. The trade-off
is that voice quality and availability are the platform's, and a long reply is
spoken for as long as the platform takes — the bar has a Stop button and the
transcript is on screen. `docs/decisions.md` records why no vendor was added.

**Every reply can be played, not only inside a voice turn.** A speaker button
next to the assistant's name reads that message aloud; a second click stops it.
This is the manual half of the same module, so it shares the Markdown reduction
and the Stop semantics. It is also the only way to hear an old conversation.

**The voice and the rate are settings, and the identity is provider-scoped.**
The volume button in the chat header opens Voice / Rate / Preview. The saved
value is `{provider, voice, rate}`, not a bare voice name: a name is not unique
across engines, a browser voice exists only on the machine that enumerated it,
and a supplier voice is a server-side catalog entry. `browser` is the only
provider implemented; when a TTS binding is added, its voices join the same
structure as another provider and the saved choice is never sent to the wrong
engine. A saved browser voice that is missing on this machine falls back to
automatic rather than failing, and the menu clears it once the catalog is known.

**The catalogs are not comparable, so the picker is bounded.** Edge/Linux
exposes 321 voices, including 14 Chinese "Online (Natural)" ones; Firefox's
speech-dispatcher backend expands every espeak language into all of its variants
— 14,805 voices, 945 of them English. Rendering that would freeze the page, so
the picker keeps up to 50 voices for the console's two languages (English and
Chinese) and one representative for every other language, always including the
saved voice. Automatic selection is not restricted: `utterance.lang` still gets
a voice for any language the reply is written in, whether or not it is pinnable.

**A dictated turn says so.** The chat request carries `input: "voice"`; the host
adds a concision instruction to the system prompt for that turn — answer as
speech, two or three short sentences, direct answer first, no tables, headings,
code blocks or long lists, and tolerate recognition errors by answering the
intent. The transcript still stores ordinary user and assistant blocks; the
modality is a property of the turn, not a new file format. The phone sends the
same field from its wake turn, so both clients get the spoken-answer shape.

Two behaviours are deliberate and easy to mistake for bugs:

- The transcript is **sent automatically**, not inserted into the composer. A
  voice conversation that required a keypress per turn would not be hands-free.
- After the reply is spoken the microphone opens again. That loop is the
  feature; Cancel ends it, and the "Read replies aloud" switch (persisted) turns
  only the speech off.

**What was verified here.** On the development machine, in headless Firefox
driven over WebDriver BiDi:

- The real microphone opens through the app's own recorder and the level meter
  follows it (5–34 % of the meter for room noise; a person speaking drives it
  higher).
- A recorded Mandarin clip, injected as the microphone stream, was uploaded as
  RIFF / mono / 16 kHz / 16-bit PCM (164,568 bytes), transcribed by the real
  `meetings.transcribe` binding as `你好，问你今天天气怎么样？`, sent as a chat
  turn, answered, spoken, and the loop returned to listening with a second
  `getUserMedia` call. Cancel released every track (`readyState === 'ended'`).
- A refused permission, a quiet turn and a stalled stream each end with their
  own message, and neither the quiet nor the stalled turn uploads anything.
- The Chinese UI and the dark theme render the bar.
- The dictated turn reached `POST /assistant/chat` with `input: "voice"`; the
  per-message play button spoke the reply and a second click stopped it; the
  settings menu offered automatic voice selection and four rates, and Preview
  produced speech.
- In headless Edge, the same menu listed 321 voices with 14 Chinese ones; a
  chosen voice (晓北) was persisted as `{provider: "browser", voice: …}` and the
  Chinese preview was spoken with that voice and audible on the sink monitor
  (peak RMS 5,658).

**What is not verified.** The owner's own voice and how often the vendor
mishears it; spoken-reply quality on this host (Firefox exposes no voice list
yet speaks through speech-dispatcher — see the lessons doc); Safari and
Chromium; and a real HTTPS deployment, where the origin must be secure for
`getUserMedia` to exist at all (the bar says so when it is not).

## The phone talks back

The Android client reads replies with the phone's own engine
(`android.speech.tts.TextToSpeech`, part of the platform since API 1). Like the
console's browser voices this is no vendor and no network: the engine ships with
the device, works offline and costs nothing per reply. The paid call stays the
one ASR call per turn.

```
voice turn reply → ChatViewModel.sendText(input = "voice")
  └─ settings.voiceOutput.enabled ? speak(reply)
       └─ SpeakableText.reduce — the console's Markdown-to-speech rules
            └─ SpeakableText.chunk — sentence-sized utterances
                 └─ AndroidSpeaker: setLanguage / setVoice, setSpeechRate, speak
                      └─ UtteranceProgressListener → speaking = false
```

Three decisions are worth knowing before changing this:

- **The rate and the on/off switch are the app's; the engine and the voice are
  the system's.** Android already has a text-to-speech settings screen with
  per-language defaults, downloads, and a preview, so the app does not
  reimplement a voice picker that could disagree with it: it honours the
  selected voice and only overrides it when a saved name matches one the engine
  reports. This is the one place where the phone deliberately offers less than
  the console, whose voices are per-browser and have no system equivalent.
- **Only a dictated turn is spoken automatically.** A typed turn stays silent —
  the screen is already in front of the owner — and it can still be read on
  demand with the speaker button on the reply, which is also how an old
  transcript or a reply after Cancel is heard.
- **The wake service is paused while the phone speaks.** A reply leaves through
  the loudspeaker and returns through the microphone; an answer that contains
  "winnie" would otherwise start a turn of its own. `ACTION_PAUSE` stops the
  detector, `ACTION_RESUME` brings it back when speech ends, and the service
  stays alive so the notification and the setting do not flicker.

The settings structure is `{provider, voice, rate, enabled}` — the console's
`{provider, voice, rate}` plus the switch — so a future supplier TTS binding
adds a provider rather than a second settings shape. It lives in
`SharedPreferences` on the phone because the voices it names exist only there.

## What Android allows, and what it does not

This is the part that decides how "always listening" really behaves. None of it
can be fixed in the app.

- **No low-power path.** Google's hotword runs on a DSP that third-party apps
  cannot use. This detector is a normal `AudioRecord`, so it costs CPU and
  battery, and it competes with every other capture app.
- **Foreground service, started from a visible screen.** The service type is
  `microphone`, which Android 14 refuses to start from the background. Listening
  therefore starts when the owner flips the switch (or opens the app with it
  already on) and then survives screen-off, task removal and process death.
- **No boot start.** Android 15 forbids starting a `microphone` foreground
  service from `BOOT_COMPLETED`. After a reboot the owner opens the app once;
  `MainActivity` then restarts the service if the setting is on. The app does not
  try to work around this with a `specialUse` service that opens the microphone
  later — that would be hiding a microphone behind a service type that does not
  describe it.
- **Background activity launch is refused.** `SecurityException` is not thrown;
  the start is simply ignored. So the detection always posts a high-priority
  notification as well, and that notification is the reliable path into the
  turn. When the screen is on and Winnie is in front, the direct start works and
  the turn opens without a tap.
- **One microphone, one winner.** Android 10 and later give the microphone to one
  capture at a time; another app receives silence. The detector therefore stops
  *before* the activity records, and comes back when the turn ends or after 60 s
  if the owner ignores the wake. While listening, another app that records (a
  voice message, a call recorder) may receive silence — that is the honest cost
  of an always-on microphone, and it is why the switch is explicit.
- **The privacy indicator stays on.** Android 12 and later show a microphone dot
  for as long as any app captures. The service notification says the same thing
  in words, and its Stop action switches listening off.
- **OEM killers.** Some ROMs kill foreground services anyway. The app already
  asks for the battery-optimisation exemption for the push service; the wake
  service needs the same treatment and is not separately exempted.

## Cost

| Item | Cost |
|---|---|
| Licence | 0 (Apache-2.0) |
| Per wake | 0 — no network, no vendor |
| APK growth | ~5.3 MB model + ~15 MB native library per ABI |
| Voice turn | one ASR call on the `meetings.transcribe` binding (paid) |
| Spoken reply | 0 — the browser's and the phone's own voices, no vendor |
| Battery | the real price; unmeasured on a device (see below) |

The wake detector and the voice turn are deliberately separate costs: the part
that runs all day is free, and the part that costs money runs once per turn, for
one utterance.

## What is implemented

- On-device keyword spotting with a committed model and keyword file.
- A `microphone` foreground service with a visible notification and a Stop
  action, restarting after process death, and refusing to lie when the
  permission is missing (it switches itself off).
- Two-second pre-roll carried through the intent, so the turn starts at the wake
  word.
- Energy-based endpointing, unit tested.
- A voice bar in the chat that replaces the composer while a turn runs, with
  Cancel and a failure message.
- `POST /api/v1/assistant/transcribe`: multipart WAV in, joined text out, on the
  same ASR binding as meeting notes, with 400/413/422/502/503 distinguished.
- A wake switch on the Account tab that requests the microphone permission and
  starts the service from a visible screen.

Console (same document, previous section):

- A microphone button in the chat composer that starts a continuous voice
  conversation: listen, transcribe, send, speak the reply, listen again.
- Browser capture through an AudioWorklet to a 16 kHz mono WAV, with the phone's
  endpointing rules and a 3 s stall / 25 s length guard.
- Spoken replies through the platform's `SpeechSynthesis`, with a persisted
  "Read replies aloud" switch, a Markdown-to-speech reduction and a play/stop
  button on every reply.
- Distinct messages for a refused, missing, busy or insecure microphone, a turn
  with no speech, an ASR outage and a speech-synthesis failure.
- A speaker button on every assistant message, a Voice/Rate/Preview menu with a
  provider-scoped saved choice, and a bounded catalog that survives
  speech-dispatcher's 14,805 variants.
- A dictated turn is marked `input: "voice"`, so the model answers for the ear
  instead of writing a document.

Android, on top of the wake turn:

- The phone reads a dictated turn's reply aloud with the platform's
  `TextToSpeech`, through the same Markdown reduction in Kotlin
  (`audio/SpeakableText.kt`) as the console.
- A speaker button on every reply: read it, stop it, and hear an old transcript
  or a typed turn.
- A Voice output card on the Account tab: read replies aloud (on by default),
  four rates, and a preview sentence.
- The wake word service pauses while the phone speaks and resumes when it stops.

## What was measured, without a phone

The Android detector cannot run here, but the same sherpa-onnx 2.0.1 release,
the same ONNX files and the same keyword file run on the desktop. Three results
decided the shipped configuration:

1. **The pipeline is sound.** The model's own `en_0.wav` (a real recording)
   triggers the release's own `LIGHT UP` keyword and reports it. So file syntax,
   asset names and the decode loop are right.
2. **Synthetic speech is useless for this check.** `espeak-ng` audio of "light
   up" does **not** trigger the release's own `LIGHT UP` keyword, at any
   threshold down to 0.01. The model is trained on real speech and a formant
   synthesizer is out of domain; an espeak miss therefore says nothing about a
   human miss. Do not "fix" the keyword file because of a TTS miss.
3. **A real voice needed a variant and zero trailing blanks.** A real recording
   of "Winnie the Pooh" (Lingua Libre via Wikimedia Commons, 1.15 s, converted
   to 16 kHz mono) decodes as `W EH1 N IY0` in the model's phoneme output, so the
   `W IH1 N IY0`-only file missed it at every threshold and every blank count.
   Adding the `EH1` variant and setting `numTrailingBlanks = 0` makes it fire
   (`winnie`), while the ten real recordings in the model's `test_wavs` produce
   **no** false hit with the six-line file.

What that does not prove: a wake **rate** (one speaker, one utterance), a false
accept **rate** over hours of television and conversation, battery, or anything
about how the service behaves on the phone.

The check is committed as `scripts/check-wake-keywords.py`, so editing
`keywords.txt` does not have to rely on a remembered experiment:

```bash
python3 scripts/check-wake-keywords.py \
  --model .tmp/kws/sherpa-onnx-kws-zipformer-zh-en-3M-2025-12-20 \
  --hit path/to/a/real/winnie.wav
# 1 wake recordings, 9 decoys, 0 failures
```

It exits non-zero when a wake recording misses or a decoy fires, and it mirrors
`WakeWordDetector.config()` — same assets, same score, same threshold, same
trailing-blank count. `WakeKeywordsTest` covers the cheaper failure in the JVM:
every token in the file must exist in `tokens.txt`.

## What is not verified

There is no Android device or emulator on the development machine, so the
following are implementation claims, not measurements:

1. **Wake rate and false accepts.** Needs 20 wakes at three distances plus an
   hour of ordinary speech with the phone in the room. Then tune the boosting
   score and threshold, and record the numbers here.
2. **Battery.** An overnight run with the screen off, comparing the same night
   with listening off. If the cost is unacceptable the answer is a "listen while
   charging" switch, not a quieter lie.
3. **Microphone contention.** Record a voice message in another app while
   listening; confirm the detector pauses or the other app gets silence, and
   document which.
4. **The Android 14/15 service rules on the target ROM**, including whether a
   foreground service started before screen-off keeps the microphone after the
   device is locked, and whether an OEM battery saver kills it.
5. **The model loads from the APK.** The desktop run proves the files and the
   keyword file; loading them through `AssetManager` inside the AAR's JNI is
   still a device-only check.
6. **The speech engine actually speaks.** The phone's voices are a device
   property, and Robolectric cannot bind to a synthesiser service, so the
   JVM tests prove the text reduction and the "no engine" failure path only.
   Which Chinese voice the phone picks, whether it speaks at all when the
   engine is missing its language data, and whether the paused detector really
   stops hearing the loudspeaker are device checks: plug in a phone, open
   Account → Voice output → Preview, and then ask a question by voice and watch
   the microphone indicator. A ROM with no Chinese voice is the case to try
   deliberately.

Until those five are done, this feature is "implemented, not validated on a
phone", and the README says so.
